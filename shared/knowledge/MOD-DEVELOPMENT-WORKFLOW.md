# Project Zomboid 모드 공통 개발 방식

이 문서는 Auxilia's Crossbow를 개발하며 정리된 작업 방식을 다른 Project
Zomboid 모드에서도 재사용할 수 있도록 일반화한 가이드다. 아래의 파일명과 명령은
이 저장소를 예시로 들지만, 핵심은 특정 아이템이나 기능이 아니라 **검증 가능한 작은
변경을 만들고 실제 게임에서 확인한 근거를 남기는 과정**에 있다.

## 1. 기본 원칙

### 실제 대상 버전을 기준으로 삼는다

기억이나 오래된 위키보다 설치된 목표 버전의 스크립트, 아이템, 레시피, 모델과 실제
실행 결과를 우선한다. 개발을 시작할 때 지원할 게임 버전과 플레이 환경을 명시하고,
확인하지 않은 환경은 지원한다고 표현하지 않는다.

### 원본과 생성 결과를 구분한다

직접 수정해야 하는 원본과 도구가 만드는 결과물의 위치를 분명히 한다. 이 프로젝트에서는
Blender 생성 스크립트와 아이콘 원본이 `source-assets`에 있고, 게임이 읽는 완성 파일은
`workshop` 아래에 있다. 생성 결과를 손으로 고치면 다음 생성 때 변경이 사라지므로 항상
원본 또는 생성기를 수정한다.

### 가장 작은 수직 단면부터 완성한다

여러 아이템과 변형을 한꺼번에 추가하지 않는다. 대표 아이템 하나에 대해 등록, 표시,
제작, 장착, 사용, 저장과 불러오기까지 전체 경로를 먼저 연결한다. 이 단면이 실제
클라이언트에서 동작한 뒤 같은 구조를 다른 등급이나 재료로 확장한다.

### 검증을 한 단계에 몰아넣지 않는다

검증은 다음처럼 비용이 낮은 순서로 쌓는다.

1. 생성기 자체 검사: 모델 크기, 재질, UV, 이미지 투명도처럼 생성 시 알 수 있는 조건
2. 정적 검사: 필수 파일, ID 참조, 번역 키, 레시피 입출력과 메타데이터의 일관성
3. 로드 검사: 깨끗한 서버 또는 클라이언트가 오류 없이 모드를 읽는지 확인
4. 상호작용 검사: 장착, 제작, 발사, 드롭, 저장과 불러오기 등 실제 플레이 동작 확인
5. 회귀 검사: 수정한 기능과 인접한 기능이 함께 유지되는지 확인

자동 검사는 “파일이 맞게 생겼는가”를 빠르게 확인하고, 게임 테스트는 “엔진이 실제로
어떻게 해석하는가”를 확인한다. 둘 중 하나로 다른 하나를 대체하지 않는다.

### 결론보다 근거를 기록한다

“잘 작동함”만 남기지 말고 게임 버전, 모드 버전, 시험 환경, 재현 단계, 원시 수치,
로그와 스크린샷을 함께 남긴다. 실패도 원인과 수정 후 재검사 결과를 기록하면 다음 모드의
설계 자료가 된다.

## 2. 모노레포 권장 구조

모드의 성격에 맞게 이름은 바꿀 수 있지만 역할은 분리하는 편이 좋다.

| 위치 | 역할 |
|---|---|
| `mods/<slug>/workshop/` | 게임 또는 Workshop에 그대로 배포할 수 있는 모드별 완성 트리 |
| `mods/<slug>/source-assets/` | Blender, 이미지 원본, 생성 스크립트 등 모드별 재현 가능한 소스 |
| `mods/<slug>/tools/` | 기능과 자산을 깊이 검사하는 모드 전용 도구 |
| `mods/<slug>/docs/` | 밸런스, 테스트 결과처럼 해당 모드에만 적용되는 근거 |
| `shared/knowledge/` | 버전별 엔진 동작과 모든 모드가 재사용할 개발 지식 |
| `shared/lua/` | 명시적 매핑으로 각 배포 트리에 동기화하는 공통 런타임 코드 |
| `shared/branding/` | 썸네일·포스터·아이콘의 공통 제작 규격과 템플릿 |
| `config/project-zomboid.json` | 모든 모드가 따라야 하는 목표 게임 버전 |
| `config/mods.json` | 모드 ID, 경로, 패키지명, 공통 코드 매핑의 등록부 |
| `tools/` | 전체 검증, 패키징, 배포와 공통 코드 동기화 |
| `mods/<slug>/VERSION` | 모드마다 독립적인 사용자 버전 |

배포 트리는 저장소의 다른 자료에 의존하지 않고 독립적으로 설치할 수 있어야 한다.
반대로 로그, 원본 파일, 생성 중간물은 배포 트리에 섞지 않는다.

## 3. 기능 개발 순서

### 3.1 범위와 완료 조건을 먼저 쓴다

구현 전에 다음을 짧게 정한다.

- 목표 게임 버전과 지원 환경
- 플레이어가 얻게 될 동작
- 변경하지 않을 항목과 이번 버전의 비목표
- 기존 저장과 호환되어야 하는 내부 ID
- 자동으로 검사할 조건과 사람이 게임에서 확인할 조건

내부 ID는 저장 데이터와 다른 파일의 참조점이 될 수 있다. 표시 이름을 개선하는 일과
내부 ID를 바꾸는 일을 분리하고, 꼭 필요한 마이그레이션 없이는 출시된 ID를 유지한다.

### 3.2 바닐라 동작을 조사한다

비슷한 바닐라 아이템이나 레시피를 여러 개 찾아 비교한다. 필드 이름만 복사하지 말고
단위, 기본값, 태그의 부작용, 모델 좌표계, 애니메이션 연결과 런타임 초기화 시점을
확인한다. 중요한 판단은 비교표나 설계 문서에 출처가 되는 게임 버전과 함께 남긴다.

바닐라와 다른 동작이 필요하다면 차이와 이유를 명시한다. 확인하지 못한 엔진 동작을
추측으로 문서에 확정하지 말고, 작은 실험으로 먼저 검증한다.

### 3.3 대표 수직 단면을 구현한다

가장 단순한 대표 사례 하나를 다음 순서로 연결한다.

1. 모드와 리소스 등록
2. 아이템 또는 기능의 데이터 정의
3. 필요한 Lua 이벤트와 상태 전환
4. 모델, 텍스처, 아이콘과 애니메이션 연결
5. 레시피, 전리품 또는 다른 획득 경로
6. 영어와 한국어 등 지원 언어의 표시 문자열
7. 디버그 환경에서 빠르게 재현할 시험 도구

대표 사례가 로드만 되는 상태에서 멈추지 말고, 플레이어가 처음 획득해 핵심 행동을
마치고 저장한 뒤 다시 불러오는 경로까지 확인한다.

### 3.4 변형을 확장한다

등급, 재료, 언어 같은 변형은 공통 규칙과 차이점을 표로 정한 뒤 확장한다. 복사한 정의는
누락과 잘못된 참조가 생기기 쉬우므로 ID 목록, 번역 키 대응, 모델 매핑, 수치 범위를
정적 검사에 추가한다.

수치를 조정할 때는 한 번에 가장 작은 관련 값만 바꾸고, 바닐라 기준 또는 플레이 기록과
비교한다. 여러 값을 동시에 바꾸면 무엇이 결과를 만들었는지 판단하기 어렵다.

## 4. 반복 검증 흐름

각 의미 있는 변경은 아래 순서로 확인한다.

1. 원본 또는 생성기를 수정하고 필요한 산출물을 다시 만든다.
2. 모드 전용 검사와 루트 `tools/validate.ps1 -Mod <slug>`를 실행한다.
3. 배포 트리를 전용 시험 폴더에 통째로 교체한다. 이 프로젝트의
   루트 `tools/deploy.ps1 -Mod <slug>`처럼 이전 파일이 남지 않게 하고, 복사 전후 내용을 비교한다.
4. 깨끗한 서버 또는 클라이언트에서 로드하여 등록, 파싱, 참조와 초기화 오류를 찾는다.
5. `docs/TESTING.md`처럼 재현 가능한 절차로 실제 플레이 동작을 확인한다.
6. 실패를 수정한 뒤 같은 조건으로 다시 시험하고, 인접 동작도 회귀 확인한다.
7. 확인한 환경과 결과를 연대기식 스모크 테스트 기록에 추가한다.

게임 테스트에서는 기존 캐시나 오래된 설치 파일이 성공처럼 보이게 만들 수 있다. 따라서
새 설치, 전용 시험 저장, 현재 배포 트리라는 조건을 구분해 사용하고, 시험용 Lua나 아이템이
일반 배포에 들어가지 않았는지 마지막에 확인한다.

## 5. 테스트 설계

좋은 테스트 항목은 결과를 관찰할 수 있고 다시 실행할 수 있다. 예를 들어 “모델 확인”보다
“좌우 방향의 대기·조준·사용 자세에서 양손이 지정된 부분에 있고 몸통을 관통하지 않는다”가
낫다.

기능마다 최소한 다음 범주를 고려한다.

- 정상 경로: 획득부터 핵심 행동 완료까지
- 경계 조건: 빈 상태, 최대·최소 수량, 부족한 기술과 잘못된 작업 위치
- 상태 전환: 장착과 해제, 장전과 해제, 중단과 재개
- 보존: 저장과 불러오기, 재접속, 기존 저장 데이터
- 표현: 모델 방향과 크기, 아이콘, 문자열, 지원 언어
- 오염 확인: 다른 바닐라 레시피나 태그에 의도치 않게 포함되지 않는지
- 통계 동작: 확률 기능은 충분한 표본의 원시 횟수를 기록하는지

버그가 발견되면 가능하면 재현 조건을 자동 검사나 고정된 스모크 테스트 항목으로 바꾼다.
같은 유형의 문제가 다시 생겼을 때 출시 전에 잡히도록 하는 것이 수정의 일부다.

## 6. 문서화와 의사 결정

문서는 작업 일지가 아니라 다음 결정을 돕는 기준이어야 한다.

- 설계 문서: 엔진 제약, 좌표계, 데이터 흐름과 선택 이유
- 밸런스 문서: 비교 기준, 수치, 역할과 의도한 장단점
- 테스트 절차: 누구나 반복할 수 있는 준비와 합격 조건
- 스모크 테스트 기록: 실제로 시험한 버전, 환경, 결과와 발견한 문제
- 로드맵: 다음 범위, 순서, 비목표와 출시 조건
- 안정화 규칙: 어떤 보고를 즉시 고치고 무엇은 증거를 더 기다릴지

코드와 문서가 같은 사실을 중복해서 갖는 경우 정적 검사로 차이를 탐지한다. 버전, 레시피
수, 번역 키, 필수 파일처럼 출시를 막아야 하는 사실은 사람이 기억해서 맞추지 않는다.

## 7. 패키징과 출시

출시 후보는 개발 폴더를 수동으로 압축하지 않고 항상 같은 패키징 도구로 만든다. 이
모노레포 루트의 `tools/package.ps1`은 다음 원칙의 예시다.

- 패키징 전에 전체 정적 검사를 통과시킨다.
- `VERSION`과 모든 메타데이터의 버전을 일치시킨다.
- 압축 파일의 경로, 파일 수, 크기와 해시를 배포 원본과 비교한다.
- 배포 파일과 SHA-256 체크섬을 함께 만든다.
- CI에서도 같은 검증과 패키징 절차를 실행한다.
- 태그의 버전과 소스의 버전이 일치할 때만 릴리스를 만든다.

최종 테스트는 가능하면 개발 트리가 아니라 실제로 배포할 패키지를 깨끗하게 풀어서
수행한다. 출시 후에는 치명적 오류, 잘못된 참조, 밸런스 의견을 같은 우선순위로 취급하지
말고 미리 정한 안정화 기준으로 분류한다.

## 8. 새 모드 시작 체크리스트

- [ ] 목표 게임 버전, 지원 환경과 비목표를 적었다.
- [ ] 설치 가능한 배포 트리와 원본·작업 산출물을 분리했다.
- [ ] 유사한 바닐라 구현을 실제 목표 버전에서 조사했다.
- [ ] 저장 호환성을 고려한 네임스페이스와 내부 ID 규칙을 정했다.
- [ ] 대표 기능 하나의 수직 단면을 실제 게임에서 완주했다.
- [ ] 생성 검사, 정적 검사, 로드 검사와 상호작용 검사를 구분했다.
- [ ] 번역, 모델, 아이콘, 레시피와 Lua 참조의 대응을 검사한다.
- [ ] 깨끗한 로컬 배포와 시험 저장을 재현할 수 있다.
- [ ] 테스트 절차와 합격 조건을 문서화했다.
- [ ] 패키지 내용이 배포 원본과 동일한지 자동으로 감사한다.
- [ ] 버그와 밸런스 보고에 필요한 증거와 처리 기준을 정했다.

이 체크리스트를 모두 채우는 것 자체가 목표는 아니다. 새 기능을 작게 연결하고, 가장 싼
검사부터 실제 플레이까지 단계적으로 확인하며, 확인한 사실을 다음 변경에 재사용할 수 있게
남기는 것이 공통 작업 방식의 핵심이다.
